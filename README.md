# Enterprise Data Analyst Agent

A fork of [langchain-ai/open_deep_research](https://github.com/langchain-ai/open_deep_research) (MIT) that turns the
research agent into an analyst for **structured internal data plus documents**: read-only SQL, sandboxed Python,
hybrid document retrieval, cross-session memory, and a service layer — with every claim backed by a frozen,
reproducible experiment in [`EVIDENCE.md`](EVIDENCE.md).

> **中文简介**：在 open_deep_research（LangGraph 多智能体研究框架）上扩展出面向"结构化数据库 + 内部文档"的数据分析 Agent：
> 只读 SQL 与 Docker 沙箱 Python、向量 + BM25 + RRF 混合检索、工具调用容错（超时/退避重试/熔断/模型降级）、
> 记忆与注入防护、FastAPI + Redis 服务层，以及协议先冻结再运行的评测。所有数据均为合成数据，不含任何企业数据。
> 详细实验记录见 [`EVIDENCE.md`](EVIDENCE.md)（中文）。

**All data in this repository is synthetic or public.** The demo databases, knowledge bases, company names and
customers are generated by scripts in `my_extensions/`; nothing here comes from a real company.

## What this fork adds

| Area | What it does | Code | Evidence |
|---|---|---|---|
| Structured data | Read-only `sql_executor` (SELECT allow-list, read-only connection, `ATTACH` blocking, timeout) | `src/open_deep_research/sql_executor.py` | §10, §51, §60, §63 |
| Code execution | `python_executor` in a Docker sandbox for pandas-style analysis | `python_executor.py` | §11, §46 |
| Document RAG | Title-based chunking, vector + BM25 + RRF hybrid retrieval, rerank, replaceable Faiss / pgvector backends, citation verification | `internal_doc_search.py`, `hybrid_retrieval.py`, `rerank.py`, `faiss_store.py`, `pgvector_store.py`, `citation_verification.py` | §6–§8, §34, §38, §41, §43 |
| Reliability | Per-tool timeout, exponential-backoff retry, circuit breaker, model fallback, disclosure of degraded runs, loop detection, run tracing | `tool_reliability.py`, `model_fallback.py`, `run_trace.py` | §1–§4, §28, §65 |
| Memory | `mem0` cross-session memory with a two-layer admission filter (rules + optional LLM judge) | `memory_manager.py`, `memory_guard.py` | §14, §30, §61, §64 |
| Safety | Human approval for high-risk tools, indirect-prompt-injection filter for retrieved documents, write-intent detection | `approval.py`, `doc_content_guard.py`, `write_intent.py` | §15, §53, §57, §66 |
| Service | FastAPI + Redis: async jobs, idempotency keys, rate limiting, SSE, Prometheus metrics, MCP server | `api_service.py`, `mcp_server.py`, `deploy/` | §16, §22, §26, §44 |
| Evaluation | Eval harness with frozen protocols, SQL-computed expected answers, paired tests, budget brake | `my_extensions/PROTOCOL_*.md`, `agent_eval_*.py` | §9, §18, §20 |

Optional behaviours are off by default and switched on by environment variables (`ODR_*`, see
`my_extensions/PROTOCOL_*.md` for the exact settings of each experiment).

## Selected results

Everything below is from one model family (`gpt-4.1-mini`) on **synthetic** data with author-written questions.
Read the caveat column before quoting a number.

| Question | Result | Scope and caveat | Evidence |
|---|---|---|---|
| Fewer model calls per question? | 13.30 → **4.40** on average (3 runs, sd 0.06); tokens −67.6% | 63 questions, config `ODR_DIRECT_RESEARCH=1 ODR_SQL_SCHEMA_HINT=1 ODR_SKIP_COMPRESS=1 ODR_SKIP_BRIEF=1`. Quality did not drop: the single-run pass-count increase is not significant (§45), while the 3-run per-question analysis shows pass rate 0.836 → 0.889 (p = 0.005, v1 scorer; §69). Reproduced on a new database with 40 new questions: 12.50 → 4.38. | §45, §56, §59, §62, §69 |
| Do tool / iteration limits explain the cost? | **No measurable effect** from relaxing or tightening them | Controlled ablation, two runs of the baseline differ as much as the treatment does | §31, §37 |
| Does adding a document-title header to chunks help retrieval? | Hybrid (RRF) Hit@1 0.808 → **0.962** (+8 / −0, exact sign test p = 0.0078) | 52 answerable frozen queries over a 46-chunk synthetic KB; confirmatory, not blind (author had seen earlier results); gain may partly come from repeating company names in each chunk | §43 |
| Faiss / pgvector instead of the baseline store? | Identical first-hit rank on 87 queries (0 differences) | Equivalence, **not** a speed-up | §38, §41 |
| Does retry + circuit breaker help under faults? | Tool-call success 70.0% (21/30) → **96.2%** (25/26) with 30% injected retrieval failures | Real model, 16 questions, small number of calls | §28, §65 |
| Can the SQL tool be made to write? | **0 / 361** write attacks succeed (naive writable baseline: 234 / 361). False blocks on 226 benign read-only queries: 8 → **0** | Offline, deterministic author-written corpora, no model in the loop. The 8 → 0 needs `ODR_SQL_ALLOW_WITH=1` (default **off**, which rejects every `WITH …` query); its effect on end-to-end pass rate with a real model was not measured | §60, §63 |
| Memory admission filter | Held-out malicious phrasing blocked: rules 5/31 → rules + LLM judge **30/31**; benign memories wrongly dropped 0/41 → **2/41** | Judge is not perfectly stable at temperature 0 (±1 on boundary cases) | §61, §64 |
| Indirect prompt injection in documents | Rule-based filter blocks explicit injections (7/8) but **not paraphrases** (0/4) | Author-written cases; online baseline is rarely induced, so the effect cannot be measured end-to-end | §53, §57, §66 |
| Continuous integration | 44 offline scripts + pytest modules, including a real PostgreSQL + pgvector service | `.github/workflows/tests.yml`; no API cost | §55, §67 |

## Quick start

```bash
git clone <this-repo> && cd <this-repo>
uv venv && source .venv/bin/activate
uv pip install -e ".[test]"
cp .env.example .env                     # add OPENAI_API_KEY (and TAVILY_API_KEY for web search)
python my_extensions/setup_demo_db.py    # generates a synthetic demo.db (companies + funding rounds)

# Offline tests: no real API calls, no cost (a fake key is enough)
export PYTHONPATH=src OPENAI_API_KEY=sk-fake-test-key-no-real-network-calls
python my_extensions/test_sql_executor.py
python my_extensions/test_hybrid_retrieval.py
```

Run the agent with the LangGraph dev server as in the upstream guide ([`docs/UPSTREAM_README.md`](docs/UPSTREAM_README.md)),
pointing it at a database with an **absolute** path:

```bash
export ODR_SQL_DB_PATH="$(pwd)/my_extensions/demo.db"
uvx --refresh --from "langgraph-cli[inmem]" --with-editable . --python 3.11 langgraph dev --allow-blocking
```

## Reproducing the experiments

Each experiment has a protocol that was committed **before** the run (`my_extensions/PROTOCOL_*.md`), a script
(`my_extensions/run_*.sh`, `agent_eval_*.py`, `eval_*.py`) and raw results (`my_extensions/eval_results/`,
`sql_guard_audit_results/`, …). Paid runs with `gpt-4.1-mini` cost roughly $0.5–0.7 per 63-question pass; the SQL
guard, memory filter and injection-mechanism evaluations are offline and free.

## Limitations

- One model (`gpt-4.1-mini`), mostly single runs, synthetic data, author-written questions and labels.
- The robust effects are cost, safety-mechanism behaviour and retrieval ranking on this corpus; answer-quality gains are modest and measured only on this question set.
- Keyword-based tool routing can be bypassed by rephrasing; the rule-based injection filter does not catch paraphrases.
- Memory uses a fixed user id (single-user demo); the local Qdrant store does not support multi-process access.
- Two tests compare against historical commits of the private development history; in this public single-commit
  repository they print a skip message instead of running that comparison.
- `EVIDENCE.md` records negative and null results on purpose (for example §31, §37, §23); please read it before citing numbers.
